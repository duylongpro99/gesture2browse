# 1D.5 — Diagnostics screen — design spec

Validated design for milestone 1D.5 (roadmap §4.4). Produced by `obra-brainstorming`;
owner intent from session -1, three design decisions from the session-0 owner gate
(Q1=A, Q2=A, Q3=C). This spec answers the five questions (`CLAUDE.md §1`); the
five-question form lives in `1D.5-diagnostics.md`, the tasks in `.impl.md`.

## Problem

The owner runs a daily tuning loop (roadmap §4.6) that must "report numbers from
diagnostics, not impressions" (roadmap §7, risk §9 row "owner tuning loop becomes
the bottleneck"). There is no screen that surfaces those numbers. Today the live
telemetry in `chrome.storage.session` carries **fps only** (`PumpStat`) plus the
FSM transition log (`TransitionLogEntry`); per-stage timings and dropped-frame
counts exist only in the **offline `BenchRow` CSV**, and there is no place to
record which gestures fired wrongly.

## Owner intent (session -1)

A **standalone full-tab page** (its own entrypoint, like `grant-camera` — not a
side-panel tab) surfacing live health of the `capture → landmarks → gesture-core →
action` pipeline so the owner can tune thresholds and catch regressions.
First-class must-haves: **fps + per-stage timings**, **dropped-frame count**, and a
running **false-positive log** (gestures that fired but should not have) — the
false-positive log and stage timings are the primary tuning signals. A **JSON
export** button dumps current metrics + false-positive entries in structured form
that feeds the owner's offline threshold-tuning loop (replayable against fixtures).
It renders metrics and logs only; it owns no gesture-timing constants (single owner
stays `gesture-core`).

## Owner decisions (session-0 gate)

- **Q1 = A.** Include the live producer in 1D.5: extend the offscreen worker to emit
  per-stage timings + a dropped-frame count, and extend `PumpStat` **additively**
  (optional fields, protocol-first, both sides). Perception + protocol are pulled
  into this milestone; owner accepts the ~2–3 session cost. All gesture-timing
  constants stay in `gesture-core`.
- **Q2 = A.** The false-positive log is **owner-annotated**: the page renders the
  live gesture/intent/transition stream and the owner taps *flag as false positive*,
  which writes a `FalsePositiveEntry`. No on-page heuristic (an auto-detector would
  put gesture-timing judgment on the page — forbidden, single owner is `gesture-core`).
- **Q3 = C.** A **record-landmarks toggle, default OFF**. The export **always**
  carries a short per-entry window of `GestureFrame` **features** (FSM-level replay
  via `replayFrames`). When the toggle is **armed**, the offscreen worker keeps a
  rolling **raw-landmark** buffer and a flagged entry also carries a landmark window
  for **full-pipeline replay** via `replayFixtureWith` — the arch §1/§6 recording
  exception, which `.claude/rules/offscreen.md` already blesses ("landmarks … not
  persisted unless the user records custom gestures **or opts into diagnostics**").

## The five questions

### 1. Placement

Cross-component milestone, joined by `packages/protocol` messages. One owner each:

| Concern | Owning component | Rule file |
|---|---|---|
| Diagnostics full-tab page (render, annotate, export) | **new** `apps/extension/entrypoints/diagnostics/**` | **new** `.claude/rules/diagnostics.md` |
| Emit per-stage timings + dropped frames; rolling landmark buffer when armed | offscreen worker `apps/extension/entrypoints/offscreen/**` | `.claude/rules/offscreen.md` |
| Persist extended `PumpStat`; keep a rolling `GestureFrame`-feature window; build + persist `FalsePositiveEntry`; relay record-arm/disarm | service worker `apps/extension/entrypoints/background*` | `.claude/rules/background.md` |
| `PumpStat` extension; `FalsePositiveEntry`; `DiagnosticsExport`; `DiagnosticsConfig`; `FrameSample` | `packages/protocol` | `.claude/rules/protocol.md` |
| `DiagnosticsExport` → replay-input conversion | `packages/gesture-core` (owns replay + `FrameInput`) | `.claude/rules/gesture-core.md` |

The message that joins offscreen→SW is the additively extended **`PumpStat`** (adds
`stages`, `dropped`) and the recording-armed **`GestureFrame.landmarks`** (already
optional in the schema). The page↔SW↔storage shapes are **`FalsePositiveEntry`**,
**`DiagnosticsConfig`**, and the export envelope **`DiagnosticsExport`**. New
entrypoint dirs are auto-discovered by WXT (like `grant-camera`), so no
`wxt.config.ts` change is required.

### 2. Boundary check

- **diagnostics page** (new rule, modeled on `sidepanel.md` + `grant-camera.md`):
  may depend on React, `protocol`, `chrome.storage` (session/local), `chrome.runtime`,
  `chrome.tabs`. Must never: render or retain raw video/`VideoFrame`/`ImageBitmap`
  (it may render the exported/stored **landmark** points as a skeleton, never raw
  video); network calls; secrets; a gesture-timing constant (single owner is
  `gesture-core`); a `confirm()`. Reads every stored blob through its `protocol` Zod
  schema before rendering (page-is-hostile applies even to our own stored data).
- **offscreen**: emitting **numeric** stage timings + a dropped count is measurement,
  not timing logic — allowed. The rolling landmark buffer is the diagnostics
  recording exception the rule already names. Offscreen must never touch
  `chrome.storage`, so the landmark window leaves only over the Port (as
  `GestureFrame.landmarks` when armed); the SW persists it. No gesture-timing logic
  added.
- **service worker**: persisting the extended `PumpStat`, the feature window, and
  `FalsePositiveEntry` to `chrome.storage.session` is diagnostic, not a secret —
  allowed. Validates every inbound frame/message with the Zod schema (already does).
- **protocol**: additive only; depends on `zod` only. `PumpStat` new fields are
  `.optional()` so every existing 0B producer stays valid.
- **gesture-core**: the export→`FrameInput[]` / export→`FixtureRecord` helpers are
  pure data mapping over shapes it already owns; no new runtime dependency.

### 3. Interfaces touched

Protocol-first, all additive:

- `PumpStat` (`pump.ts`) **+=** `stages?: StageTimings`, `dropped?: number`
  (`StageTimings = {captureMs, inferMs, normalizeMs, classifyMs, filterMs}`, echoing
  the `BenchRow` per-stage names so timings have one vocabulary across the protocol).
- **new** `FrameSample` — a `GestureFrame`-feature slice (`ts, present, gesture?,
  score, pinch?, velocity`), no landmarks; the always-present replay window.
- **new** `FalsePositiveEntry` — `{ts, eventTs, note?, transition?: TransitionLogEntry,
  frameWindow: FrameSample[], landmarkWindow?: FixtureFrame[]}`.
- **new** `DiagnosticsConfig` — `{recordLandmarks: boolean}` (the toggle).
- **new** `DiagnosticsExport` — `{schema:'gesture-diagnostics/v0', exportedAt,
  fps: PumpStat[], transitions: TransitionLogEntry[], falsePositives:
  FalsePositiveEntry[], config: DiagnosticsConfig}`.

`GestureFrame` is **not** changed — `landmarks?` already exists ("only when
recording"); recording-armed simply populates it.

### 4. Principle check (`docs/02-architecture.md §1`)

- **Two loops, two speeds** — diagnostics is off the hot path: it reads storage
  snapshots and `chrome.storage.onChanged`, at human pace. Recording-armed adds a
  landmark payload to the Port **only when armed**; steady state is unchanged. The
  feature window the SW keeps is a bounded ring over frames it already receives.
- **Video stays in one process** — the principle most at risk, and the reason Q3=C
  defaults OFF: raw video never leaves offscreen; landmarks leave only under the
  explicit diagnostics recording exception; the page renders points, never pixels.
- **Page is hostile** — every stored blob is re-validated with its Zod schema before
  the page renders it.
- **Agent proposes, human disposes** — n/a (no agent); the false-positive log is
  purely human annotation.
- **Replaceable parts** — the page is a pure function of `protocol` shapes and owns
  no timing constant; swapping the producer or the classifier changes nothing on the
  page.

### 5. Tests

- **Consumer-side contract tests** (frozen this session, `## Exit checks` I-rows):
  extended `PumpStat` (additive + stages/dropped), `FalsePositiveEntry` shape, and
  `DiagnosticsExport` → replay round-trip through `gesture-core`'s public export.
- **Unit (Vitest)**: `StageTimings`/`FrameSample`/`FalsePositiveEntry`/
  `DiagnosticsExport` schema round-trips; the offscreen stage-timer and landmark
  ring buffer (pure modules, no browser globals, mirroring `fps-logger.ts`); the SW
  false-positive builder (bounded series) and the page's export builder + view
  formatter (pure).
- **e2e (Playwright, fake webcam y4m)**: launch the unpacked extension, open the
  diagnostics page, assert fps / per-stage timing / dropped-frame readouts render
  from seeded `storage.session`, flag a false positive, click export and assert the
  downloaded JSON parses as `DiagnosticsExport`, and capture the screenshot the
  owner reviews (roadmap §4.4 Exit).
- No gesture-timing/threshold constant changes here, so **no fixture replay is
  required** for correctness; the export→replay contract exercises the replay path
  as a consumer.

## Scope / YAGNI

In: the page, the live producer (stage timings + dropped frames), the
owner-annotated false-positive log, the record-landmarks toggle (default off), JSON
export, and the consumer-side replay conversion helpers. Out: charts/graphing
libraries (numeric readouts + simple sparkline from stored series only), auto
false-positive detection (Q2), any gesture-timing constant, settings that change
behaviour (calibration/settings are 1D.2/1D.3), CSV export (JSON only, per intent),
and streaming raw video anywhere.

## Session budget

~2–3 sessions (owner-accepted, Q1): (1) protocol + offscreen producer; (2) SW +
page + export; (3) e2e + owner screenshot review, plus slack for the record-landmarks
path. Exact task split is in `.impl.md`.
