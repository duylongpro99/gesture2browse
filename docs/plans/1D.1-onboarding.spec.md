## Owner intent (session -1) — the WHAT this spec realizes

First-run/onboarding for the M1 developer preview; primary user **Maya** (Accessibility).
Job-to-be-done: get a first-run user from install to "I can point and click," with
**informed consent**, in the fewest steps. In scope: (1) consent + privacy up front,
leading with the differentiator that **video never leaves the device** (only landmarks
cross process boundaries) and explaining `<all_urls>`; (2) hand off to the **existing
full-tab grant page** (0C/G2), steering to "Allow on every visit"; (3) **profile
selection, default Accessibility**; (4) land on a **"you're ready"** state pointing to
the cheat sheet (1D.6). Depth: **minimal-but-complete** (consent → camera grant →
profile → done). **No** guided gesture walkthrough (defer to 1D.6 — supersedes the
roadmap row's "60-second tutorial" wording). Calibration: 1D.1 **links** to 1D.2, does
**not** run it inline. Out of scope: gesture tutorial (1D.6), inline calibration (1D.2),
any agent/voice onboarding (Phase 2).

**Production bar — unhappy paths are required, not optional:** camera denied or "Allow
this time" chosen → detect and re-route to the grant page with guidance; no webcam →
clear dead-end, no hang; `<all_urls>` restricted → explain what breaks, offer
continue-degraded or retry; a **full screen-reader + keyboard-only path** through the
entire flow (gestures are not configured yet, so onboarding must be completable without
them).

The intent note says scope/interface boundaries belong to this plan and its
`.claude/rules` — the intent sets the WHAT, not the HOW. No conflict with the intent
surfaced while designing; the HOW decisions below are the plan's to make.

## Design decisions (the HOW, delegated to this plan)

### D1 — Surface: a new full-tab entrypoint `apps/extension/entrypoints/onboarding/**`

A first-run wizard is a full-tab flow: it opens on install, hands off to the full-tab
`grant-camera` page and back, and must be a clean screen-reader/keyboard target.
`docs/02-architecture.md §3.4` already puts the camera grant on a full tab; 1D.5 set the
precedent of adding a **new** full-tab entrypoint (diagnostics) that the §4.4 surface
list did not pre-name, and it was accepted. The side panel (§3.4) remains the steady-state
UI; onboarding is the one-time first-run surface that ends by pointing at it. New rule
`.claude/rules/onboarding.md` (header-glob form, like `grant-camera.md`/`diagnostics.md`).

### D2 — Onboarding never touches video; it delegates capture to `grant-camera`

The single most-at-risk principle (video stays in one process, arch §1/§6). Onboarding
does **not** call `getUserMedia` and renders no video. For its readouts it uses only
`navigator.mediaDevices.enumerateDevices()` (device kind — is a `videoinput` present)
and `navigator.permissions.query({name:'camera'})` / the stored `CameraGrantStatus`
(permission state). The actual grant — the one surface where `getUserMedia` runs and
every track is stopped at once — stays in `grant-camera` (0C). Onboarding opens that page
in a tab and watches `chrome.storage.session.cameraGrantStatus` for the result.

### D3 — Minimal shared settings interface fixed here, in `packages/protocol`

Onboarding must persist the chosen profile, and today `Profile` exists only informally in
`background/dispatcher.ts` (`'standard' | 'accessibility'`) with the background pump
hardcoding `'standard'`. So this milestone promotes it to a protocol Zod shape and adds a
minimal persisted `Settings` and `OnboardingState`:

- `Profile = 'accessibility' | 'standard' | 'presenter'` (arch §3.2, PRD FR-31; default
  **accessibility**). All three names are fixed now (they are the product's profile
  vocabulary); the **picker** offers only Accessibility + Standard, the two with distinct
  dispatcher behavior today (YAGNI — Presenter has no behavior until it earns one; 1D.3
  adds it to the picker when it does).
- `Settings = { profile }` — the minimal user-preference record, stored in
  `chrome.storage.sync` (arch §3.2 "user overrides stored in `chrome.storage.sync`").
  1D.3 (settings) extends it **additively** (camera pick, gesture map, snap radius,
  trusted-click…); 1D.2 (calibration) writes its tunables into the same record.
- `OnboardingState = { completed, completedAt?, version }` — stored in
  `chrome.storage.local` (device-local: re-onboard per device). `version` lets a future
  onboarding re-trigger without clobbering settings.

These are additive; no frozen 1A/1B/1C member is redefined. Profile is **not** a secret,
so `chrome.storage.sync`/`local` is allowed (the "never" is secrets, not preferences).

### D4 — The profile choice becomes real in the same milestone

Otherwise onboarding's default-Accessibility pick would be inert. Background reads
`Settings.profile` (Zod-validated) at startup and on `storage.onChanged`, and feeds the
existing dispatcher `profile()` getter (the 1C comment already anticipates "1D swaps in
real switching"). This makes the Accessibility default actually turn on dwell-click. Only
the profile *selection* moves to the SW; every gesture-timing **constant** (dwell 600 ms,
etc.) stays in `gesture-core` — background selects a profile, it does not own timing.

### D5 — First-run trigger and the pump gate live in the background

`runtime.onInstalled` (reason `install`) opens the onboarding tab. The existing camera
pre-check gate additionally routes to onboarding (not straight to the pump) while
`OnboardingState.completed` is false. On finish the page sends an `OnboardingComplete`
envelope (Zod-validated on the SW side); the SW runs its existing grant gate and starts
the pump. This keeps the SW the single owner of offscreen/pump lifecycle.

## The flow (minimal-but-complete)

A linear wizard; each async wait uses an `aria-live` status region; focus moves to the
new step's heading on advance; every control is a real `<button>`/`<a>` reachable by Tab.

1. **Welcome + consent / privacy.** Lead: *your camera video never leaves this device —
   only hand-position landmarks (points) are shared between parts of the extension.*
   Explain camera use and why the extension needs access to every site (`<all_urls>`: to
   draw the cursor and click where you point). Primary: **Continue**.
2. **Camera.** `enumerateDevices` → if no `videoinput`: **dead-end** copy ("No camera
   detected. Connect one and choose Recheck."), a **Recheck** button, no hang. If a
   camera is present, read permission (`CameraGrantStatus` / `permissions.query`):
   - granted + persistent → advance;
   - otherwise → **Set up camera** opens `grant-camera.html` in a tab with the "Allow on
     every visit" steer; the page watches `storage.session.cameraGrantStatus`
     (`onChanged`) and advances on a persistent grant. A non-persistent/"Allow this time"
     or denied result → re-route guidance + **Try again** (re-open the grant page).
3. **Site access.** `permissions.contains({origins:['<all_urls>']})` → full: "Ready on
   every site." Restricted: explain what breaks (cursor/click only work on sites you
   allow), then **Grant access to all sites** (`permissions.request`; if not grantable at
   runtime, guidance to the extension's site-access setting) or **Continue in limited
   mode**. (May render as a subsection of step 1's consent; the detection + degraded copy
   are what matter.)
4. **Profile.** Radio choice, **Accessibility preselected** (with a one-line description
   of each) + Standard; writes `Settings.profile` to `chrome.storage.sync`.
5. **Ready.** "You're ready to point and click." **Calibrate** (opens the side panel; the
   real calibration lands in 1D.2) and **Cheat sheet** (disabled "coming soon" until
   1D.6). Writes `OnboardingState.completed = true` to `chrome.storage.local` and sends
   `OnboardingComplete` to the SW.

## Isolation / testability

`entrypoints/onboarding/steps.ts` is DOM-free and `chrome.*`-free: it holds the pure
decisions (device-presence → outcome; camera-status → next step; host-access → mode;
default profile; step ordering) and is unit-tested in node. `App.tsx` owns all I/O
(storage read/write with Zod validation, `tabs`, `permissions`, `runtime` messaging).
This mirrors diagnostics' `view.ts`/`export.ts` vs `App.tsx` split.

## The five questions (summary; full form in `1D.1-onboarding.md`)

1. **Placement.** New `entrypoints/onboarding/**` (page, owner) + `background.ts`
   (trigger/gate/profile-read) + `packages/protocol` (the shapes). Joining messages:
   `Settings`/`OnboardingState` (page↔storage↔SW), `OnboardingComplete` (page→SW),
   reused `CameraGrantStatus` (grant-page→storage→page).
2. **Boundary.** New `.claude/rules/onboarding.md`: React, `@gesture/protocol`,
   `wxt/browser` (`storage` local+sync / `runtime` / `tabs` / `permissions`),
   `navigator.mediaDevices.enumerateDevices` + `navigator.permissions` (readouts only),
   DOM; **never** `getUserMedia`/video/`VideoFrame`, network, secrets, gesture-timing
   constants, `confirm()`, direct `zod`; Zod-validates every stored blob. `background.md`:
   reads a non-secret `Settings` from `storage.sync`, validates every inbound message.
   `protocol.md`: additive, `zod`-only. No deviation, no ADR.
3. **Interfaces.** Additive, protocol-first (Task 1): `Profile`, `Settings`,
   `OnboardingState`, `OnboardingComplete`. No frozen member redefined.
4. **Principles.** *Two loops two speeds* — human-pace UI, hot path untouched. *Video in
   one process* (most at risk) — onboarding never captures/renders video; grant stays in
   `grant-camera`. *Page is hostile* — every stored blob re-validated with Zod. *Agent
   proposes/human disposes* — n/a. *Replaceable parts* — page is a pure consumer of
   protocol shapes, owns no timing constant.
5. **Tests.** Per-task unit tests (schemas; pure `steps.ts`; background profile-read/gate
   helpers); two frozen consumer-side contract tests (1D.3 settings-profile;
   1D.3 onboarding-state); Playwright e2e (fake webcam) covering the two roadmap Exit
   criteria + the unhappy paths + keyboard/aria path. No timing constant changes → no
   fixture replay required.

## Out of scope (YAGNI)

Gesture tutorial/walkthrough (1D.6); inline calibration (1D.2); the Presenter profile's
behavior and its picker entry (1D.3); camera picker / gesture-map editor / trusted-click
toggle / snap-radius UI (1D.3); any agent or voice onboarding (Phase 2); a persisted
"onboarding step reached" resume cursor (the flow is short; restart from step 1).
