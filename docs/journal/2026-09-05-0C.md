**Key finding — the plan §2 open question is resolved:** the MV3 **service worker _can_ answer `navigator.permissions.query({name:'camera'})`** in this Chromium build (E2 diagnostic `queryAnswered: true`, `source: 'sw-query'`). So the background gate queries the permission directly; the last-`CameraGrantStatus`-from-`storage.session` fallback stays in the code for any build/context where the SW query throws, but was not exercised.

**Design choices made while implementing**
- **Gate routes to the grant page only on a _definitive_ not-granted signal** (a successful SW query, or a stored `CameraGrantStatus`, that is not `granted`). On `unknown` (SW can't query *and* nothing stored) it proceeds to `ensureOffscreen()` — blocking on uncertainty would strand a working pump and, in particular, would have regressed G1. The offscreen `getUserMedia` is the ultimate test in that case.
- **`RunCameraPrecheck` message** re-runs the gate and, if granted, recreates the offscreen document so its `getUserMedia` runs under the now-granted permission — this is how E2 proves assertion (c) deterministically despite the SW-startup vs `grantPermissions` race. (A service worker never receives its own `runtime.sendMessage`, so the e2e sends it from the page context and ignores the expected no-response rejection.)
- Reused the pure `deriveGrant` helper in `background.ts` (single source of the persistence derivation) rather than a second inline copy.

**No regression:** G1 `frame-pump.e2e.ts` stays green with the gate in front of `ensureOffscreen()` — full 60 s window, p05 30.0 fps, only `about:blank` open (no grant tab), because the fake-ui G1 context reports `granted`/proceeds. Left `frame-pump.e2e.ts` unchanged.
